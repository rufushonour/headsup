# AGENTS.md

Guidance for AI coding agents working in this repo. See `README.md` for the user-facing
description of the app; this file focuses on what an agent needs to build, verify, and
change the code safely.

## What this is

Heads Up (`HeadsUp`) is a macOS menu-bar app, built with Swift Package Manager (no
`.xcodeproj`). It's a single executable target under `Sources/HeadsUp`, mixing AppKit
(window/menu chrome) and SwiftUI (view content), plus the Sparkle framework for
auto-updates. There is no server component, no other language, no monorepo — everything
lives in this one package.

## Build & verify

```
swift build                     # compile check, fastest way to verify a change builds
./Scripts/build_app.sh          # debug build -> build/HeadsUp.app (proper bundle + Info.plist)
./Scripts/build_app.sh release  # release build
open build/HeadsUp.app
```

`swift run` works but calendar permission prompts attach to whatever process invokes
EventKit, so `swift run`'s prompt attaches to the toolchain process, not "HeadsUp" — use
the packaged `.app` (`build_app.sh`) whenever a change touches `CalendarService.swift` or
anything else that needs a real Calendar permission grant.

**No automated test suite exists.** `swift build` (or a release build) is the correctness
bar for compilation; there's nothing to run for behavioral tests. For anything touching
UI, alert presentation, or calendar behavior, build and run the `.app` and exercise it
manually — the menu bar dropdown's "Send Test Alert" item is the fastest way to trigger
the full-screen alert without waiting for a real meeting.

Don't add a test target speculatively — if you add real tests, wire them into
`Package.swift` as a proper `testTarget` and mention it here.

## Code layout

- `CalendarService.swift` — EventKit access, polling, alert scheduling/snooze, today's meetings.
- `MeetingLink.swift` — join-link detection (Zoom/Meet/Teams/Webex/etc. from URL, location, or notes).
- `AlertPresenter.swift` / `AlertView.swift` — the full-screen alert (one borderless window per screen).
- `MenuBarController.swift` — status item, today's meetings list, quick actions.
- `SettingsView.swift` / `SettingsWindowController.swift` — Settings window.
- `WelcomeView.swift` / `WelcomeWindowController.swift` — first-launch onboarding.
- `AppDelegate.swift` / `main.swift` — wiring and entry point.
- `Resources/Info.plist` — bundle metadata, including the Calendar usage description and
  the app version (`CFBundleShortVersionString`) used by the release pipeline.
- `Scripts/` — build, packaging, and release automation (see below).

## Conventions

- Reference types are `final class`; views and value types are `struct`.
- No singletons — dependencies (e.g. `CalendarService`) are constructed once in
  `AppDelegate` and passed in; cross-component communication uses closure properties
  (`onMeetingDue`, `onTestAlert`, `onQuit`, ...) rather than delegate protocols or
  NotificationCenter. Follow this pattern for new wiring rather than introducing a new
  communication style.
- AppKit owns windows/menus; SwiftUI owns view content inside them (see
  `SettingsWindowController` / `WelcomeWindowController` for the pattern of an
  `NSWindowController` hosting a SwiftUI view).
- No SwiftLint/swift-format config is present — match the formatting already in the
  surrounding file (4-space indent, trailing closure style for the callback pattern above).

## Release pipeline — handle with care

`Scripts/cut_release.sh <version>` bumps `Resources/Info.plist`, commits, pushes to
`main`, and pushes a `vX.Y.Z` tag. The tag push triggers
`.github/workflows/release.yml`, which:

1. **Verifies the tag matches `Info.plist`'s `CFBundleShortVersionString`** and fails the
   build otherwise — if you edit the version, keep both in sync.
2. Runs `Scripts/release.sh` to build the `.dmg` and produce a Sparkle-signed
   `appcast.xml` entry (EdDSA signature via `SPARKLE_PRIVATE_KEY`).
3. Commits the updated `appcast.xml` back to `main` and publishes the GitHub Release.

Implications for agents:
- Don't hand-edit `appcast.xml` — it's generated by `Scripts/release.sh` and overwritten
  on every release.
- Never commit a Sparkle private/signing key. `SPARKLE_PRIVATE_KEY` is a GitHub Actions
  secret (and Keychain-backed locally for `Scripts/release.sh`'s local path); it must
  never appear in source, scripts, or commits.
- Don't invoke `cut_release.sh`, push tags, or otherwise trigger the release workflow
  unless the user explicitly asks to cut a release — it pushes to `main` and publishes a
  public GitHub Release.

## Toolchain note

Built with Xcode 14.1 / Swift 5.7 (`swift-tools-version:5.7` in `Package.swift`), which
caps the SDK at macOS 13 — this is why `CalendarService` uses the legacy
`requestAccess(to:)` EventKit API instead of the macOS 14 granular permission API. Don't
"modernize" this to the newer API without checking the toolchain has actually moved past
this constraint.
